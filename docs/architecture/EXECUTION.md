# Simulation, AI features, and exports

## Run lifecycle

1. The browser submits the current `Project` to `POST /api/runs`.
2. FastAPI/Pydantic validates structure, including the subsystem rules in `server/hierarchy.py`. Empty models fail immediately. The job runner checks the drawing-only subsystem placeholder, required inputs on every sheet, signal bus widths (`server/buses.py`), and subsystem ports the active variant lacks, before numerical execution.
3. `server/modelica.py` emits a complete Modelica model from the snapshot (see [emission](#emission)). Built-in physical kinds use canonical wrappers; MSL wrapper blocks instantiate their library class; signal and generated physical components use bounded definitions with standard Modelica connectors; subsystems become nested models.
4. `server/engine.py` records the snapshot and source in a unique run directory and runs it on the selected backend: a generated `.mos` script with the built-in engine's `omc` (installed apps), with the host `omc`, or `engine_runner.py` in the engine container.
5. OpenModelica loads MSL, compiles, initializes, and simulates. The adapter requires explicit successful completion, a result file, sufficient coverage, and finite preview data.
6. The service saves a result preview and retains full CSV output. The browser polls the job and renders results or diagnostics.

Failures raise `SimulationFailure` (`server/diagnostics.py`). Its message is the readable text stored as the job `error`; its structured `Diagnostic` list is stored as the job `diagnostics` (see the [job contract](../API.md#job-contract)). Validation and safety problems name their blocks and ports directly. For solver text, `failure_diagnostics` makes one entry per compiler `Error:` line, maps instance IDs that appear as component references, and, for singular linear systems, names the signal blocks on a direct-feedthrough cycle (a block whose equations use `der`, `sample`, `delay`, or `pre` breaks the cycle). Engine start-up failures are `engine` diagnostics. Once a run folder exists, a failure also writes `diagnostics.json` beside `model.mo`, and `GET /api/runs/{runId}/diagnostics` returns it. Successful runs parse solver warnings into `result.problems` and keep the raw `diagnostics` string.

The job registry is in memory. API job statuses are `queued`, `running`, `complete`, `failed`, and `cancelled`. At most four operations are active across all job kinds. Engine execution has its own two-slot semaphore. Restarting the service loses job status; it does not delete completed run directories. There is no durable queue or automatic resume.

## Emission

`emit_project` writes one package `Gradara` with a `model System` at the end. Each block on the top level is one component of `System`, named by its block ID, and each connected net becomes `connect` equations.

**Equation blocks.** Signal blocks, generated blocks, and built-in kinds with a canonical wrapper get their own class, `Component_<block ID>`, with standard connectors for their ports and `parameter Real` declarations. The instance sets every parameter value.

**MSL wrapper blocks.** A definition with `modelica` gets no class of its own. `server/msl.py` checks the wrapper against `server/msl_index.json` (see the [model format](MODEL_FORMAT.md#blocks-and-definitions)) and emits one declaration of the library class. Parameter values are substituted into the modifier expressions, and dotted keys become nested record modifications, so the battery stack block emits `Modelica.Electrical.Batteries.BatteryStacks.CellStack cell(Np=(1), Ns=(96), cellData(OCVmax=(4.2), OCVmin=(2.5), Qnom=(5)*3600, Ri=(0.005)));`. `connect` lines use the mapped MSL connector names, such as `meter.i[2]`. MSL 4.1.0 must be loaded, as it already is for every run.

**Subsystems.** Every definition reachable from the top level is emitted once, children before parents, as `model Sub_<definition ID>`. Its boundary blocks become the model's own connectors, named by the boundary block ID: `RealInput`/`BooleanInput` for inports, `RealOutput`/`BooleanOutput` for outports, and the domain's physical connector for connports. Wires to a boundary block connect to that connector directly. Inner equation blocks get classes named `C_<definition ID>_<block ID>`. Each promoted parameter is `parameter Real par_<ID>`, and the inner blocks it targets take `par_<ID>` instead of their own value. An instance is a component `Sub_<ref> <block ID>(par_<ID>=<value>, …)`. Two instances of one definition share one class. A version 1 document has no subsystems and emits no `Sub_` classes.

**Signal buses.** A port with a `width` of two or more is an array connector (`RealOutput y[3]`), and a `connect` between two such ports joins the whole array. The editor derives every width from the wiring (`propagateBuses` in `lib/gradara/buses.ts`); the service trusts the stored widths but checks them first (`bus_problems` in `server/buses.py`): every port on a net must carry the driver's width, a Demux must split its input evenly, a Bus Selector's names must exist on its bus, and each bus block's output widths must follow from its inputs. The bus blocks' equations are generated from their ports and never taken from the document: a Mux or Bus Creator is `y = {u1, u2}` or `y = cat(1, {u1}, u2)` with a vector input, a Demux is `y1 = u[1:2]`, and a Bus Selector is `y1 = u[3]` or `y1 = u[{1, 2}]` for a sub-bus. Subsystem boundary connectors and idle ports take the width of their port (an idle bus output gives `fill(0, n)`).

**Variants.** Only the active variant is emitted, because the instance's `ref` is the active inside. When the active inside lacks some of the instance's ports and the variant marks them not used here, the instance uses a wrapper class `Sub_<ref>__idle_<hash of the port IDs>` that extends `Sub_<ref>` and adds the missing connectors as idle ports: an output gives `0` (or `false`), an input is left unread, and a physical port carries zero flow (`i`, `tau`, `f`, `Q_flow`, or `Phi` equal to 0; each pin of a three-phase plug). A missing port that is not marked fails validation before emission with one `validation` diagnostic per port. Run validation covers the top level and the insides reachable through active variants; problems inside an inactive variant do not block a run. Inactive variants are not emitted. `POST /api/variants/check` (`server/variant_check.py`) checks them separately: for each inactive variant, the model with only that instance switched (`hierarchy.with_variant`) is validated like a run and compiled with `checkModel(Gradara.System)` without simulating, one variant at a time. The workbench starts it after edits settle when the engine is ready and no run is active.

## Engine supervision

Three backends run the same job folder (`server/engines.py`). The **bundled** backend is the default in installed apps. On Windows and Linux it runs the OpenModelica tree in the app's `resources/engine` folder exactly like a native install, with `OPENMODELICAHOME`, `OPENMODELICALIBRARY` (only the bundled MSL), and the library path pointed at the bundle; OpenModelica's default compiler there is clang, so both select gcc (`setCompiler("gcc")`): the Linux engine uses the system `gcc`, the Windows engine the MinGW `gcc` it carries. On macOS it is `VmBackend`: `EngineVM` starts vfkit, which boots a Linux kernel with a read-only squashfs root (OpenModelica, gcc, MSL) using Apple's Virtualization framework, shares only the data folder over virtio-fs at `/data`, and has no network device. The service sends each command (`omc` on the generated script, `gcc`, the compiled program) to the guest agent (`packaging/engine/guest/agent.py`) over vsock, which vfkit exposes as a Unix socket; host paths under the data folder map to `/data/…`. The VM starts on the first engine request, stays up while the service runs, and stops with the service (lifespan shutdown, an exit hook, and the app's process-group stop); a stale vfkit from a crashed service is stopped on the next start. The agent kills a command's process group when it exceeds its timeout or when the service closes the connection (cancellation). A command whose output reports a gcc `internal compiler error` runs again, up to twice, since a crashed compiler inside the VM is not a model error (it has been seen under nested virtualization on CI Macs); `make` rebuilds only what did not finish. The **native** backend drives a host OpenModelica install with a generated `.mos` script. Bundled and native backends run as the user (the VM's commands run inside the VM), so definition text is screened by `server/safety.py` first. The **Docker** engine is `gradara-engine:1.27.0`, built from the OpenModelica 1.27.0 OMPython image with MSL 4.1.0. The image runs as an unprivileged user. Simulation containers disable networking, drop Linux capabilities, disallow privilege escalation, and limit resources to 2 CPUs, 2 GiB memory, and 256 processes. They mount their job directory, not the entire repository. Host Docker access remains part of the trust boundary. Every backend reports a model that fails to compile or simulate the same way: the run fails with the compiler's text, which diagnostics then explain. Only a missing or broken engine or a library that will not load counts as the engine being unavailable; a timeout (`EngineTimeout`) is a run failure, explained in terms of the model's simulation settings.

Numerical operations have a 120-second process timeout. While a run executes, `server/engine.py` checks the size of `simulation_res.csv` every second and cancels the run when it passes 1 GB (`RESULT_LIMIT`): reading such a file would exhaust memory, and it nearly always means the solver is stepping back and forth across a switching threshold. Cancellation terminates the supervised process and removes its named container. Preserve cleanup in exceptions, timeouts, service shutdown, and user cancellation when editing this adapter. Agent generation and C compilation have separate lifecycle code; do not assume they share every engine cleanup guarantee.

**Simulation settings.** A document's optional `simulation` object ([model format](MODEL_FORMAT.md#simulation-settings)) chooses the solver and its settings; absent fields use the defaults, DASSL with tolerance `1e-6` and 6,000 output intervals. `server/solver.py` turns them into the `simulate(...)` call, which the service builds once and passes to every backend in the job's `request.json` (`simulate`), so the native, bundled, VM, and Docker engines run the same call. The four solvers map to OpenModelica methods: DASSL to `dassl`; Implicit Runge-Kutta to `gbode` with `-gbm=esdirk4`; Backward Euler and Runge-Kutta 4 to `gbode` with `-gbm=impl_euler` or `-gbm=rungekutta` and `-gbctrl=const` (OpenModelica 1.27 deprecates its older fixed-step `rungekutta` method). A maximum step becomes `-maxStepSize`. A GBODE fixed step equals the output interval, so a fixed-step run records every step; Gradara asks for `ceil(stop time / step)` intervals, which shortens the step slightly when it does not divide the stop time. The fields of the other solver type are kept in the document but ignored. Limits shared with the workbench are in `lib/gradara/solver-settings.json`: tolerance from `1e-10` to `1e-2`, and at most 200,000 output intervals (or fixed steps); settings over that limit, or with an interval or step longer than the stop time, fail validation with one diagnostic naming the field. The emitted model's `experiment` annotation records non-default settings (`Interval`, `__OpenModelica_simulationFlags`), so they are part of the model hash; a model with default settings emits exactly what earlier versions did. Each `result.json` records the settings the run used as `simulation` (solver, tolerance, number of intervals, and the fixed or maximum step). Measurements behind the solver choice and the help text: on the 480 VAC flyback example DASSL took 24 s, Implicit Runge-Kutta 18 s, and DASSL with a maximum step of half the switching period 12 s; DASSL with a tolerance of `1e-4` or `1e-5` instead wrote gigabytes of event rows within a minute, while IDA and Implicit Runge-Kutta did not. GBODE prints a note about numerical Jacobians that says nothing about the model; it is left out of the run's warnings.

Diagnostics for failures that the settings usually cause carry `help`, a topic of the settings guide (`lib/gradara/solver-docs.ts`, `docs/SOLVER.md`): `slow` for a timeout, `too-much-data` for the size limit, `stopped-early` for a run that ends before the stop time or whose integrator gives up, and `fixed-blows-up` for non-finite or overflowing values under a fixed step. Under a fixed step, a failed Newton iteration is reported as the step's failure, not as an algebraic loop. A diagnostic's `detail` names the solver settings the run used.

A declared maximum of 1,000 blocks in the schema is a validation bound, not a performance benchmark.

Manual models support stop times up to 86,400 simulated seconds for slow thermal/control studies, including the [data-center cooling example](../examples/DATACENTER.md). The wall-clock timeout and the default output-interval count do not grow with the stop time; a longer horizon is not a guarantee of adequate fast-event resolution or completion within the resource budget. Full-model agent planning retains its separate 60-second limit.

## Results

`result.json` includes run ID, engine label, project key, model hash, revision, full input snapshot, stop time, the simulation settings used (`simulation`), elapsed time, sample count, a common time array, signal series, the raw solver diagnostics string, and the structured warnings in `problems`. Series use component/variable keys such as `voltageProbe.y`; an MSL wrapper output uses its connector name, such as `meter.i[2]`. Inside subsystems, keys follow the instance path (`drive.gain.y` for block `gain` in instance `drive`), the readable name joins instance names with `›` (`Drive › Gain.y`), and `blockId` is the top-level instance, so selecting a series selects the subsystem block on the top level. A logged net inside a subsystem is observed through a variable `gradara_log_<path>_<net ID>` and its series also carries `path`, the instance path. A bus gives one series per signal: key `sensors.y[2]`, named by its element (`Sensors.bus.torque`), or numbered (`Mux.y[2]`) when the bus has no names. A logged bus net is an array variable, and its series are `<key>[i]`, named `<net> · <element>`.

The preview combines a reduced overview with event pairs, extrema, and a dense final window. All series use the same sample indices. The preview is not the full numerical output, and event-heavy models can still make it large. CSV downloads retain the full output file. OpenModelica can emit an extra grid row beyond the requested stop time; preview data excludes it. OpenModelica also leaves out of the CSV any variable that equals a parameter, such as a voltmeter across a DC source or a Constant's output; the service reads those from the alias and start values in `simulation_init.xml` and reports them as constant series (`result_columns` in `server/engine.py`), so every block output still appears in Results.

The latest-result lookup requires matching document identity and emitted-source hash. Layout changes should leave results valid. A failed or cancelled run must not be surfaced as a successful partial result. See [testing](../development/TESTING.md) for engine regressions and [API](../API.md) for access.

## Component generation

For installation, account ownership, and first-use troubleshooting, see [AI feature setup](../AGENT_SETUP.md). Every AI call goes through `server/llm/dispatch.py`, which routes to the provider chosen in Settings → AI: Gradara AI (hosted, prepaid credits), OpenAI or Anthropic with the user's own key, the local Codex CLI, or off. See [distribution and AI providers](DISTRIBUTION.md#ai-providers).

`server/agent.py` builds the prompt and output schema and calls `dispatch.generate`. Each call is one schema-constrained generation: OpenAI and Anthropic use strict JSON-schema output, Gradara AI forwards the schema to its gateway, and `server/llm/codex.py` runs the Codex CLI with ephemeral execution, ignored user configuration, read-only sandbox mode, and the shell tool disabled. Requests instruct the model to return data and not execute tools. The prompt contains user intent and, when refining, the selected existing definition.

The selected block type constrains the schema: scalar Real signals, electrical pins, rotational mechanical flanges, translational flanges, magnetic ports, thermal ports, or a coupling of multiple physical domains. Generated blocks cannot have Boolean or three-phase ports, cannot wrap an MSL class, and cannot be subsystems. Physical definitions may also have scalar signal ports. Server validation rejects mismatched port domains/directions, signal-only substitutes for physical requests, and refinement that changes existing terminal identity or semantics. All types support numeric parameters, declarations, equations, and a short symbol; controller export metadata is restricted to signal blocks. Generated definitions are checked by Pydantic and OpenModelica. A failed integration check can trigger one repair attempt containing the candidate and diagnostics. A successful result returns to the frontend for insertion; the subprocess does not directly edit the saved model.

Structured output from OpenAI and Anthropic accepts no length or number limits, so `strict_schema` drops them; `describe_limits` (`server/llm/schema.py`) first restates each limit in the field's description ("Limits: at most 800 characters."), for every provider. Answers are validated through `server/llm/structured.py`: free-text fields that a model class lists in `prose` (summaries, explanations, assumption lists) are cut to their limit at a sentence or word boundary, never identifiers, equations, or numbers; an answer that still fails validation gets one corrective request with the exact problems (`<attempt>-fix`), and a second failure is a readable `ProviderError`, not a Pydantic trace. Diagnosis, model planning, model assembly, model edits, and results explanations use it.

Codex CLI calls have a 180-second timeout. HTTP providers connect within 15 seconds and wait up to 300 seconds for an answer (330 through Gradara AI). A request that certainly never reached the service (connection refused, DNS, connect timeout) is repeated up to twice; so are 429 and 5xx responses, with backoff. A read timeout or a dropped connection after sending is not repeated, so one answer is never paid for twice. Network failures name their cause (certificate check, DNS, proxy, refused, closed) via `network_reason` in `server/llm/providers.py`. Prompts and responses are not kept locally unless `GRADARA_KEEP_AI_TRANSCRIPTS=1` is set (the Codex path always keeps a copy of its prompt, schema, response, and CLI log under the data folder's `agent/` directory for diagnosis). Cancellation and timeout go through `server/processes.py`: POSIX process groups on macOS/Linux, and `taskkill.exe /T /F` on native Windows to stop the generation process tree. Windows cleanup runs without a console window and reports termination failures. The Codex path on native Windows is less exercised than the HTTP providers. Ordinary simulation does not call the provider.

Successful generation establishes schema/compiler compatibility. It does not independently verify the user's intended physics. The design intentionally supports rapid authoring without inserting a separate physics-approval workflow.

## Model editing

`POST /api/models/edit` (`server/model_edit.py`) edits the open model through bounded operations; the agent never returns a Project. The request carries the prompt, the current `Project`, the UI catalog, an optional selection of block IDs, an optional `context` (a fix passes the run's problems), `verify` (default true), and an optional `previous`. The prompt contains the model without layout (no positions, sizes, routes, junctions, plots, or annotations), the selected block names, and the catalog description shared with full-model generation.

**Refine** sets `previous` to `{prompt, summary, operations}` from a proposal the user has not applied. The operations are validated like a plan's. The prompt then states the earlier request, summary, and operations, says the current model does not contain them, and asks for one complete plan with the user's revision applied. The service keeps no conversation: everything a revision needs travels in the request, and the workbench marks the earlier proposal as superseded when the revision arrives. The Proposals tab keeps one thread per model, saved on this computer through `/api/proposals/{modelId}` (`server/proposals.py`, `<data>/proposals/<modelId>.json`): the newest 60 entries within 6 MB. Deleting a run removes every results discussion that involves it.

The agent returns an `EditPlan`: a summary, assumptions, `unsupported` (non-empty refuses the request), and 1–40 operations applied in order. A refused request completes the job as `{unsupported: reason}`, which the workbench shows as a "Gradara cannot do this yet" card. The operations are `add_block`, `create_block` (at most two), `revise_definition`, `remove_block`, `rename_block`, `set_parameter`, `connect`, `disconnect`, `set_duration`, and `log_signal` (marks the net on a connected signal output as logged; the model must already have nets). At most three definitions per edit are created or rewritten; each goes through the typed component generator, with its compile check and port-preserving refinement.

`apply_operations` applies every operation or none. It resolves aliases of added blocks and rejects unknown blocks, ports, and parameters, out-of-range values, a second driver on a signal input, input-to-input or cross-domain connections, duplicate connections, and self connections. It re-validates parameter ranges and the whole document. Existing IDs, wires, nets, labels, plots, `modelId`, and `revision` are unchanged unless an operation targets them. Removed wires leave their nets, and each new wire joins (and may merge) the nets its ports are on, or gets a new hidden net.

The pipeline has two attempts. A plan that cannot be applied, or an edited model that fails `validate_simulation` or a trial `simulate`, is sent back with the error for one revision. If the second attempt fails its check, the proposal is returned with `verified: false` and structured `diagnostics` instead of failing the job. A second plan that cannot be applied fails the job; cancellation never becomes a revision. The job result is `{project, summary, assumptions, changes, operations, generated, verified, diagnostics, samples, provider}`, with `changes` as `{op, blockIds, wireIds, description}` and `operations` as the plan's operations, which a revision sends back.

The client applies a proposal with `mergeProposal` (`lib/gradara/proposal.ts`). It keeps its own objects for untouched blocks and wires, so their pinned bends and routes survive, and takes definitions, new blocks (at standard size), new wires (without routes) and the nets made for them, nets the edit marked as logged, removals, the name, and the stop time from the proposal. The agent never chooses coordinates: `layoutNewBlocks` (`lib/gradara/auto-layout.ts`) places new blocks in house style without moving existing ones. It tries positions that put a terminal on the line of the terminal it connects to, one gap along the flow, then rows below and above, and grid positions between a block's neighbours; it keeps clear of every block and its name, and picks the position whose wires (as the canvas will draw them) have the fewest bends, crossings, runs through blocks or names, and backward signal legs, then the shortest length. The result goes through one `commit`, which is one undo step. A proposal made for an earlier `revision` cannot be applied.

## Results explanation

**Run summary.** `POST /api/results/digest` (`server/run_digest.py`) summarizes one to three stored runs of a model, labelled A, B, C (A is the run asked about). It reads the full stored data through `server/run_store.py` (a small cache of recently loaded runs), never the thinned plot data, over the whole run or a window. For each chosen signal (up to 12; when none are chosen, logged signals first, 8 in all) and run it computes: minimum, maximum and their times, time-weighted mean and RMS, initial and final values, peak-to-peak, the steady value (time-weighted mean over the last 10% of the window) and ripple, settling time (inside a band of 2% of the step, widened to cover the ripple), overshoot as a percentage of the step, zero crossings, and an envelope of `[t, min, max]` points (900 in all, shared across signals and runs). Events are listed per signal: a transient, a signal that has not settled, a step (a jump of at least 20% of the range within 0.01% of the window), switching (more than six steps), and a clip (at least 2% of the window held at an extreme). With several runs it adds, for each signal, the largest and RMS difference from the baseline run (default: the last listed run), the parameters that differ, the solver warnings of run A, and up to 60 available signal names. The same request always gives the same digest. The Data Inspector's **Summary** (`components/gradara/run-summary.tsx`) shows it.

**Explain results.** `POST /api/results/explain` (`server/results_agent.py`, job kind `results`) takes the digest request, a question, and up to four earlier `{question, answer}` turns of the same discussion. The runs are read before the job is queued, so an unreadable run fails without a charge. The prompt holds the question, the earlier turns, the digest, and run A's model without layout; `POST /api/results/explain/preview` returns exactly that text. The answer (`ResultsAnswer`) has an explanation, findings and causes with evidence (`{run, signal, metric, t0, t1, at, value}`), next steps, signals that were not recorded, and an optional change to propose. It may also ask for up to four measurements (`stats`, `valueAt`, `crossings`, `correlation` between two signals); Gradara computes them from the stored data and asks once more with the results.

Every quoted number is then recomputed from the stored runs. A value matches within 2% of itself or 0.5% of the signal's range over the window; times within 2% of the window; overshoot within 1 point or 5%. A finding whose evidence does not match, or that quotes numbers with no evidence, is removed; evidence that does not match is dropped from a cause, and a cause is labelled `measured` only when it kept all its evidence, otherwise `hypothesis`. Block IDs that are not in the model are dropped. The result reports how many claims were removed. The workbench (`components/gradara/results-card.tsx`) shows each checked number as a chip that focuses the plot on it. **Propose this change** starts an ordinary model edit; after the user applies it and runs, the inspector shows the new run beside the discussed one.

## Diagnosis

`POST /api/diagnose` (`server/diagnose_agent.py`) explains problems and can propose a fix. The request carries the `Project`, 1–50 `Diagnostic` entries (live checks, the last run, or one row), an optional `runId`, the UI catalog, an optional question, and `proposeFix`. The run's emitted `model.mo` and saved solver text are added only when the run ID is alphanumeric and its `project.json` has the same `modelId` as the request; otherwise the run ID is ignored.

Stage 1 asks for a `Diagnosis`: a summary, causes (diagnostic IDs, block IDs, explanation), `fixable`, up to eight manual steps, and an `editPrompt` when a fix is possible. Unknown block and diagnostic IDs are removed. Stage 2 runs only when `proposeFix` is set and the diagnosis is fixable. It calls the model-editing pipeline with the edit prompt, the cause blocks as the selection, and the problems as `context`, with verification on. The result is `{diagnosis, proposal, provider}`, plus `fixError` when a requested fix could not be built. The job kind is `diagnose`. The workbench only starts a diagnosis when the user sends **Explain problems** or **Fix problems** from the Ask bar (opened by Explain, Fix with AI, or a row's ask button in Problems).

## Controller C code

`server/codegen.py` generates C deterministically: the same model and options always give the same files, and no AI provider is involved. The unit is one subsystem instance, or a set of blocks, on the sheet named by `path` (subsystem instance IDs from the top level).

1. **Unit.** Nested subsystems inside the unit are inlined, and every net inside it is resolved to the block output that drives it. Every block must have only signal or Boolean terminals, and no bus; a physical terminal, or a selection that shares a physical net with the rest of the model, is refused with the block IDs. For a subsystem, its inports and outports are the unit's inputs and outputs. For a selection, nets that cross its edge are inputs (driven outside) or outputs (driven inside). Each input and output records the result variable that carries it in a run, such as `sensor.y` or `drive.p_ab12`.
2. **Order.** Blocks whose output reads their input in the same step (feedthrough) run after the blocks that feed them. A cycle of feedthrough blocks is refused as an algebraic loop, naming the blocks.
3. **Templates.** Each block type has a small C template in `t_signal` (Gradara signal blocks) or `t_msl` (MSL logic blocks). A custom (AI-generated) block uses its own `definition.ctemplate` when that template's signature matches the block's equations and interface; a block without a usable template is refused by name. Parameters become fields of the `Params` struct with the model's values as defaults; they can be retuned without regenerating, except for the few structural ones the README lists (delay length, PWM carrier steps).
4. **Time.** The step is the option `step`, or else the shortest sample period in the unit, or 1 ms. Continuous states (`integrator`, `filter`, `derivative`, `pid`) are discretized with forward Euler, backward Euler, or Tustin; the state keeps its initial value on the first step. `secondOrder` uses semi-implicit Euler, `currentPI` forward Euler, and `rateLimiter` an ideal per-step slew limit, as the README notes say. Sampled blocks (`pi`, `discretePID`, `unitDelay`, `zoh`, `discreteIntegrator`) run on a counter every `period / step` steps and hold their outputs in between; a period that is not a whole number of steps is refused. Time is derived from a step counter, so it does not drift.
5. **Files.** `<prefix>.h` declares `In`, `Out`, `Params`, and `State` structs and `default_params`, `init`, and `step`; `<prefix>.c` implements them in C11 using `math.h`; `README.md` gives the call sequence, the port table, and notes. The code compiles with `gcc -std=c11 -Wall -Wextra -Werror` in `double` or `float`.

Verification (`POST /api/codegen/verify`) is a software-in-the-loop check against the last run. The run must exist and its `modelHash` must match the request, so the code and the simulation describe the same model. The unit's recorded input signals are interpolated at every controller step with cubic Hermite curves, since linear interpolation biases fast sinusoids such as motor currents and an integrating controller would drift on that bias (the later row counts at an event) and fed to the compiled code through a small host program. That program is built and run by the selected engine backend: with the built-in engine's compiler (the bundled MinGW `gcc` on Windows, the system `gcc` on Linux, `gcc` inside the engine VM on macOS), inside the engine container with no network, or with the host `gcc`/`cc` for the native backend. The outputs are compared with the recorded outputs at the same instants. Each output passes when its largest error is within 2% of its range in the run. Sampled controllers match to rounding; continuous ones differ by their discretization. The check is open-loop: it replays the plant signals the simulation produced and does not close the loop through the C code.

For a custom signal block, the Export dialog can ask the configured AI provider for a C template once (`POST /api/codegen/template`, `server/ctemplate.py`). The provider sees the block's equations, declarations, ports, and parameter values, and returns states plus output and update statements over placeholders (`{u.port}`, `{y.port}`, `{p.id}`, `{x.state}`, `{h}`, `{t}`). Every statement must be `target = expression;` with numbers, arithmetic, comparisons, `?:`, and a fixed list of math functions, and no comments, so a template cannot call anything or touch memory, even when the SIL check runs it on the host. The server checks the statements, generates a one-block unit, and compiles it; a rejection or compiler error gets one revision. The template is stored in the block's definition with a signature of its equations and interface, and code generation uses it deterministically from then on; changing the block's equations or ports makes it stale. The older whole-file export (`POST /api/exports`, `server/exporter.py`) remains in the API but the workbench no longer uses it.

Current gaps include fixed-point formats, multi-rate scheduling beyond counters on one base step, HDL targets, closed-loop co-simulation, and complete cancellation cleanup in the AI export path. These are explicit [roadmap](../../ROADMAP.md) items.

## Extension rules

Keep the frontend responsive while these operations run. Pass snapshots across the boundary, preserve diagnostics, and use structured IDs rather than filesystem paths in APIs. Keep engine-specific logic inside the adapter and emitter. A future backend must declare what component, connector, state, and event semantics it supports; replacing OpenModelica with arbitrary numerical libraries is not a drop-in change.

The current service is intended for trusted local use. Read [SECURITY.md](../../SECURITY.md) before changing transport, model validation, container mounts, agent tool access, or execution privileges.

## Inspector observations

`logging_signals.py` maps explicitly logged signal nets to their source variable. It rejects physical-net logging; sensor outputs carry those measurements. `modelica.py` emits output observation variables so the compiler retains them in CSV. Missing/non-finite logged output is a run failure, not an empty successful trace. Existing automatic output channels remain available alongside explicitly logged nets.

The dedicated Data Inspector uses a canvas renderer and frame-scheduled gestures. It loads full stored samples through the data endpoint, clips plotting to the visible time interval, preserves event pairs, and stores layouts/assignments/ranges as browser-local model preferences. It supports up to six time plots with independent Y ranges and optional linked X ranges. **Run all configurations** runs one job per configuration, each on a copy of the document with that configuration applied, and merges the results in the browser (`lib/gradara/compare.ts`): every series is renamed `[Configuration] name`, and later runs are linearly resampled onto the first run's time grid. The merged view is not saved; each run is stored as an ordinary run. Single runs are kept as a library (`components/gradara/run-library.ts`, `run-list.tsx`, `lib/gradara/run-set.ts`): `GET /api/results?model=` lists the model's stored runs without samples, the inspector shows up to three of them (the latest run plus the ones the user ticked), and each shown run's full data is fetched once through the data endpoint. A run's name lives in `meta.json` beside its `result.json`; the colour of each run and which runs are ticked are browser-local preferences per model. A plot's signals are stored as assignments (`{key, runs?}`): without `runs` a signal is drawn on every shown run that has it, with `runs` only on those, so a run opened later or a new latest run picks up the plot without reassigning anything. Each plotted line keeps its own run's sample times, so runs with different steps or stop times are drawn as recorded and nothing is resampled for display. **Compare runs** (`components/gradara/run-compare-view.tsx`, `lib/gradara/run-compare.ts`) compares the shown runs with one baseline in the browser. Signals are matched by series key. Each other run is linearly resampled with the baseline onto the union of their sample times up to the shorter stop time, with a repeated event time kept as one instant holding the value after the event. A compared sample passes when it lies between `min − m(min)` and `max + m(max)`, where `min` and `max` are the baseline's extremes over `[t − time tolerance, t + time tolerance]` and `m(v) = max(absolute, relative × |v|)`; with no time tolerance this is `|compared − baseline| ≤ m(baseline)`. Every signal is summarized per run (status, largest difference and its time, stretches outside tolerance); a signal's row is as bad as its worst run; traces are built only for the selected signal. Tolerances are browser-local preferences per model. The inspector does not yet provide per-signal tolerances, dual cursors, frequency-domain views, independently scaled dual Y axes, or live streaming.

## Full-model generation

`server/model_agent.py` orchestrates library planning, dependency generation, assembly, and trial simulation as one cancellable job. The browser sends its built-in library snapshot; the service adds the current immutable AI collection. Model assembly cannot inject definitions: it references the frozen catalog, copies definitions, applies bounded numeric overrides, and validates the resulting `Project`. Plan-time unsupported domains stop the job. Bus blocks and the empty subsystem placeholder are not offered.

Up to four missing definitions are generated sequentially through `generate_component`, with its existing selected-type contract, repair, compiler check, and archive behavior. Only after those awaits finish does assembly begin. Assembly supports up to 80 blocks and 240 connections, with distinct bounded layout cells. The frontend lays the draft out before preview and insertion with `layoutProject` (`lib/gradara/auto-layout.ts`): it tidies the agent's cells into columns and rows sized to the real blocks and straightens facing terminals, lays the model out afresh from its first source by the same rules as edits, keeps whichever scores cleaner, and then applies the Arrange command's placement (`lib/gradara/arrange.ts`, see the [wiring contract](WIRING.md#auto-arrange)) starting from that order. Layout is not solver semantics. OpenModelica must finish a full trial run. Schema, connection, or simulation errors permit one assembly repair using the diagnostic. Cancellation propagates without becoming a repair attempt. Each provider call and numerical run retains the existing timeout and process supervision; this is a bounded multi-stage workflow, not an autonomous tool loop.

The draft has no saved model identity. Acceptance saves the active document and creates a separate model using normal persistence operations. Trial artifacts keep their original identity, so the saved model must run again for its own results. Successfully generated components survive later model failure or cancellation. Jobs remain in-memory, without resume or hierarchical subsystem generation.
